# Part I. Module 01 — Naive ReAct에서 운영 가능한 하네스로

## 1. 에이전트의 진화는 '학습된 정책'과 '실행 런타임'이라는 서로 다른 축이다 (p.4)

**[원문]** RL/DQN/AlphaGo, 로보틱스, Chain of Thought, ReAct, function calling, MCP/A2A와 ACI가 발전 흐름에 등장한다. **[해설]** 이를 단일한 직선 진화사로 이해하면 오해하기 쉽다. RL은 환경에서 보상을 최대화하는 *정책 학습 방식*이고, ReAct는 LLM이 관찰과 행동을 교대하는 *추론·실행 패턴*이다. Function Calling은 행동을 구조화하는 *API 계약*이고, MCP는 도구 연결과 검색·자원·프롬프트를 다루는 *상호운용 인터페이스*다. 이들은 대체 관계가 아니라 겹쳐서 사용할 수 있는 서로 다른 계층이다. A2A는 도구 호출이 아니라 에이전트 간 작업 위임과 상태 교환을 겨냥한다. CoT 또는 추론 토큰이 명시적으로 노출되지 않더라도 모델은 `tool_calls`와 최종 답변 간 선택을 수행할 수 있다.

## 2. ReAct 내부 루프와 외부 대화 루프의 차이 (p.5–6)

한 번의 사용자 입력이 여러 LLM 호출을 유발하는 내부 루프가 있다. 한편 사용자 턴을 넘어 세션을 유지하는 외부 루프가 있다. 두 루프의 경계를 섞으면 오류가 난다. 예컨대 사용자 요청 한 건의 시간 제한은 **실행 턴 단위**에, 권한·세션 식별은 **스레드·사용자 단위**에, tool call ID 짝 맞춤은 **메시지 프로토콜 단위**에 속한다. 외부 대화가 종료되어도 비동기 워커가 살아 있을 수 있으므로 요청 수명(request lifetime)과 작업 수명(job lifetime)을 동일시하면 안 된다.

```python
# 개념용 의사 코드. 실제 SDK의 메시지 포맷 및 tool_result 짝 규칙을 준수할 것.
async def run_turn(user_msg, session, runtime):
    state = await load_checkpoint(session)
    state.messages.append(user_msg)
    while True:
        runtime.check_deadline()            # 시간
        runtime.check_step_and_cost()       # 호출/토큰/비용
        prompt = build_model_view(state)    # 불변 원본과 압축된 뷰 분리
        proposal = await call_llm(prompt)
        if not proposal.tool_calls:
            await validate_final(proposal, state)
            return proposal.content
        for call in proposal.tool_calls:
            result = await execute_through_policy(call, runtime)
            state.append_tool_pair(call, result)
            await save_checkpoint(state)    # 내구성
```

### 왜 원시 `while True`가 위험한가?

종료 여부를 모델만 결정하면 중복 검색, 실패 도구 재호출, 예상치 못한 권한 확대가 발생할 수 있다. 오류 로그만 메시지에 추가하고 외부 상태를 복구하지 않으면, 다음 관찰이 *원래 문제*가 아닌 *이전 에이전트가 만든 문제*를 반영한다. 진척을 판단하는 독립 관찰치가 필요하다. 예: 성공한 테스트 수, 실제 변경된 산출물, 해소된 체크리스트 항목, 새로운 결과 해시.

## 3. 비용이 O(N²)로 증가하는 조건 (p.7)

반복마다 k개의 토큰이 추가되고 전체 이력을 매번 다시 전송하면 호출 i의 입력이 대략 ik이다. 합계는 `k(1+2+...+N)=kN(N+1)/2 = O(N²)`. **주의**: 이차 증가는 지수 증가가 아니다. 프롬프트 캐싱으로 *요금*이 낮아져도 전송/컨텍스트 사용량과 일부 지연이 사라지는 것은 아니다. 도구 결과가 단계당 일정하지 않거나 더 많은 서브에이전트가 생기면 모델은 달라진다. 비용 관리는 토큰·API 호출 수·도구 컴퓨팅 비용·외부 서비스 과금·재시도 횟수를 따로 계측해야 한다.

## 4. 실패를 감지하는 방법과 실패에서 복구하는 방법은 분리한다 (p.7–8)

- **Detection**: 구문 검사, 테스트, 출력 스키마 검증, 불변식 검사, 중복 도구 호출 탐지.
- **Prevention**: 저장 전 AST 파싱, 타입 체크, 요청 인자 검증, optimistic concurrency check, 권한 차단.
- **Recovery**: 임시 파일 폐기, 이전 버전 복구, 새 브랜치에서 재시도, 보상 트랜잭션(compensation), 사용자 개입 요청.
- **Containment**: 샌드박스, 작업 디렉터리 제한, 네트워크 허용목록, 최소 권한, 데이터 범위 분리.

파일 변경은 원자적 교체가 가능한 경우가 있지만, 이메일 발송과 결제는 '롤백'이 아니라 별도 보상 작업만 가능할 수 있다. 따라서 부작용이 있는 도구는 **효과(effect), 반복 안전성(idempotency), 취소 가능성, 승인 필요 여부**를 메타데이터로 분류한다. `safe`, `idempotent`, `reversible`, `side_effects`, `requires_approval`은 서로 같은 차원이 아니다.

## 5. Lost in the Middle와 목표 표류 (p.8)

LLM이 오래된 지시를 항상 잊는 것은 아니지만, 대량 관찰값에서 중요한 중간 증거의 활용률이 떨어질 수 있다. 이를 단순한 'attention이 약해진다'로만 설명하면 부족하다. 실제 실무 문제는 **신호 대 잡음비 저하, 컨텍스트 창 제한, 오래된 오류 상태의 재활용, 목표와 서브태스크 간 우선순위 혼선**이 겹친다. 해결책은 긴 로그를 제거하는 것만이 아니라 `Goal / Constraints / Plan / Decisions / Evidence / Unresolved Issues`를 구별해 유지하는 것이다.

## 6. AutoGPT → Devin → SWE-agent/ACI가 의미하는 것 (p.9–11)

**AutoGPT**: 자율적으로 상위 목표를 쪼개는 아이디어를 대중화했으나 초기 도구·상태·예산 통제가 부족했다.  
**Devin**: Planner/Editor/Shell/Browser처럼 관찰과 실행을 위한 작업 환경을 구성하고 샌드박스를 제공하는 접근을 대표한다. 강의자료의 특정 SWE-bench 비교 수치는 평가 세트·시점·설정을 확인한 뒤 비교해야 한다.  
**SWE-agent**: 사람이 `cat`, `sed`로 작업하는 인터페이스(HCI)를 LLM이 잘 사용할 수 있는 인터페이스(ACI)로 바꾸는 중요성을 보여준다. 파일 조회의 작은 창, 정확한 오류 위치, 편집 실패 시 원복, 과거 관찰 압축은 모델 자체를 교체하지 않고도 성공률을 개선하는 레버다.

### ACI를 설계할 때 질문할 것

1. 결과가 비어 있으면 정상 성공인지 오류인지 모델이 분간할 수 있는가?
2. 파일 경로·라인 범위·리비전·실행 상태를 함께 보여주는가?
3. '읽기'와 '쓰기'를 다른 권한으로 구분하는가?
4. 도구가 실패했을 때 다음 행동(재읽기/인자 수정/승인 요청)이 명확한가?
5. 거대한 결과를 파일에 저장하고 필요한 부분만 다시 조회할 수 있는가?

## 7. Soft control과 Hard control: 프롬프트는 권한 시스템이 아니다 (p.12)

**Soft**: 시스템 프롬프트로 목표, 우선순위, 도구 사용 수칙을 유도. **Hard**: 실행 게이트가 역할·리소스·명령·비용을 확인하며, 모델 출력과 무관하게 거부한다. Hard control이 있다고 모든 사고가 100% 방지되는 것은 아니다. 정책 구멍, 도구 우회, 커맨드 인젝션, 외부 리소스 변경, 경쟁 상태는 별도로 검증해야 한다. 예: `runtime.context.user_id`가 사용자 메시지에서 유래하면 out-of-band라 해도 신뢰할 수 없다. 인증 서버가 검증한 principal에서 파생되어야 한다.

## 8. 미들웨어는 '정책의 위치'를 분리하고 런타임 컨텍스트는 '데이터의 경로'를 분리한다 (p.13–16)

침습적 하네스는 비용/캐시/권한/복구 분기를 하나의 `while`에 넣어 테스트와 수정을 어렵게 한다. 미들웨어로 분리하면 각 훅의 단위 테스트가 쉬워진다. LangChain 강의자료의 6개 훅은 `before_agent → before_model → wrap_model_call → after_model → wrap_tool_call → after_agent`이고, 시간상 '항상 1→2→3→4→5→6을 한 번씩' 지나가는 것은 아니다. 모델 호출과 도구 호출은 반복하며 wrap 훅은 여러 번 실행될 수 있다. 프레임워크 버전의 훅 네이밍·실행 순서는 공식 문서로 확인할 것.

**Runtime 세 스코프:**

| 종류 | 수명 | 신뢰성·변경 범위 | 예시 |
|---|---|---|---|
| `context` | 실행 요청 | 서버가 주입한 인증된 외부 값 | principal, tenant_id, 정책 버전 |
| `state` | 대화 스레드 | 스텝마다 변경되는 체크포인트 | messages, todo, pending approval |
| `store` | 스레드 바깥 | 오래 남는 공유/개인 기억 | 선호도, 프로젝트 메모, 재사용 스킬 |

`user_id`를 모델에게 인자로 직접 생성하게 하지 말고 도구 런타임이 주입하게 한다. 다만 **LLM 스키마에서 감춘다**는 것과 **모든 로그·오류 메시지·시스템 관리자에게도 비공개**라는 것은 다르다. DB 연결 객체를 프롬프트로 보내지 않는 건 보안과 비용에 모두 유리하지만 연결 풀과 수명 관리도 따로 설계해야 한다.

# Part II. Module 02 — Claude Code: 실행 제어, 프롬프트, 압축, 복구

## 9. '마이크로커널'은 유용한 비유이지 실제 OS 커널의 동일 구현을 뜻하지 않는다 (p.17–19)

강의자료는 세션 엔진을 커널, 쿼리 루프를 스케줄러, 압축 엔진을 가상 메모리, 도구 실행기를 시스템 콜, 권한 게이트를 방화벽에 대응시킨다. **[해설]** 메시지는 명확하다. LLM은 고수준 판단만 수행하고, 파일 I/O·실행 권한·복구·세션 기록은 주변 코드가 관리한다. **[검증 필요]** `98.4%`, `1.6%`, `deps.callModel()` 단일 호출 지점, 정적 프롬프트 빌더 28개 등 특정 비율과 이름은 강의자료가 다룬 코드 스냅샷의 주장이다. 범용 원칙이나 Claude Code 모든 버전에 대한 공식 보증으로 취급하지 않는다.

### 단일 공통 코어 + I/O 채널 어댑터 (p.20)

CLI, headless, 코디네이터, 원격 브리지, 상주 데몬 같은 실행 모드는 공통적인 추론·권한·메모리 코어를 공유할 수 있다. 하지만 모드별 추가 통제가 필요하다. 예컨대 headless 환경에서는 사람이 UI에서 승인할 수 없으므로 무조건 자동 승인하기보다 특정 도구만 사전 허용하고 나머지는 실패 처리한다. daemon 환경은 외부 메시지 인증, 스케줄러 내구성, 업그레이드 중인 작업 처리까지 요구한다. 강의자료에 나온 특정 명령어와 모드 존재 여부는 버전을 확인한다.

## 10. Agent-as-a-Tool: 왜 자식의 내부 로그를 부모에게 그대로 주면 안 되는가? (p.21–22)

부모 에이전트는 사용자 목표와 수용 기준을 알고, 자식은 특정 파일과 실행 로그를 자세히 안다. **컨텍스트를 격리하면 토큰은 아끼지만 정보 비대칭이 생긴다.** 그래서 지시서에는 반드시 `목표, 범위, 파일 경로, 변경 허용 영역, 완료 조건, 검증 명령, 반환 포맷, 금지 행동`을 담는다. 자식이 부모에게 반환할 것은 무작위 요약이 아니라 **검증 가능한 결과 계약**이다.

```yaml
# 설계 예: 위임 계약. Claude Code 내부 API 형식이 아님.
job_id: review-auth-42
objective: JWT 만료 검증의 경계 조건 점검
scope: [src/auth/jwt.ts, tests/auth.test.ts]
permissions: [read, run_tests]
forbidden: [modify_files, push, deploy]
acceptance:
  - 현재 구현의 결함을 재현하는 테스트 제시
  - 영향받는 입력과 예상/실제 결과 설명
return:
  status: PASS|FAIL|PARTIAL
  evidence_files: []
  risks: []
  next_steps: []
```

부모는 반환된 `PASS` 문자열만 믿지 않고 테스트 로그/산출물/커밋 해시를 별도 검증해야 한다. 부모의 목표를 빼먹어 잘못된 검증을 한 자식의 '통과'는 유효한 성공이 아니다.

## 11. 세 가지 위임 모델: 격리·포크·팀 (p.23–29)

### Specialized / isolated subagent

백지 컨텍스트에서 시작하고 작은 도구 집합만 사용한다. 독립 검색, 코드 리뷰, 테스트 등 좁은 작업에 적절하다. 전체 사용자 기록을 받지 않으므로 개인정보 노출 위험과 비용을 줄일 수 있다. 반대로 중요한 예외 조건을 지시서에서 빠뜨리면 엉뚱한 답이 나온다.

### Fork subagent

부모의 대화 맥락 일부 또는 전부를 복제한다. 사용자가 이전 대화에서 여러 개의 강력한 제약을 주었을 때 유리하지만, 컨텍스트 복제 비용과 민감정보 접근 권한이 커진다. **[검증 필요]** 강의자료의 '100% 캐시 히트=90% 절감'은 모델 제공자, 캐시 TTL, 토큰 정렬, 실제 과금에 따라 달라지는 수치이며 항상 성립하지 않는다. 캐시가 적중한다 해도 자식의 새로운 출력·툴 사용 비용은 추가된다.

### Agent Teams

장기 상주하는 여러 워커가 태스크 보드·메일박스·서로의 상태를 공유한다. 단순 호출 분산과 달리 **동시성 제어와 공유 자원 충돌**이 핵심이다. 팀원마다 같은 파일을 변경하면 충돌한다. Git worktree는 서로 다른 작업 디렉터리를 제공하지만 **보안 샌드박스가 아니며** 동일 파일의 변경을 최종 병합할 때 충돌이 생길 수 있다. 외부 DB·배포 환경·전역 자격증명은 worktree로 분리되지 않는다.

### AgentTool 7단 파이프라인 (p.27)

1. 입력 스키마 검증 → 2. 워커 종류 결정 → 3. 모델·MCP 준비 → 4. 역할별 도구 풀 구성 → 5. 필요 시 작업 트리 격리 → 6. 독립 실행 및 취소 핸들 생성 → 7. 별도 실행 기록 저장 후 요약 반환.  
**[권장]** 각 단계에 timeout, quota, trace_id를 부여한다. 도구 스키마를 숨겨도 Bash를 허용했다면 Bash를 통한 우회가 가능한지 별도 통제해야 한다. 프롬프트에 '파일 쓰지 마'라고 명시하는 것은 OS 권한 분리와 다르다.

### 동기→비동기 전환 (p.28)

`Promise.race(workComplete, backgroundSignal)`은 모델·도구 작업이 완성될 때까지 기다리거나 작업을 백그라운드로 넘기는 UI 전략이다. 부모 취소와 자식 취소를 분리하면 '사용자 화면 닫음'이 곧 '작업 중단'은 아니다. 그러나 종료된 프로세스 안의 태스크는 사라질 수 있으므로 진짜 내구성이 필요하다면 작업을 DB/큐에 기록하고 워커가 재개하도록 설계해야 한다. 출력 파일·상태·작업 ID만 반환하는 것은 프로세스 재시작 안전성을 보장하지 않는다.

## 12. ACI 도구의 정밀 설계 (p.29–31)

| 도구 | 강의자료의 가드 | 깊은 공학적 이유 | 남는 실패 모드 |
|---|---|---|---|
| Read | `offset`, `limit`, 줄 번호 | 관찰 비용 제한, 정확한 참조 좌표 | 오래된 스냅샷 읽기, 심볼 문맥 누락 |
| Edit | 선행 Read, 유일한 old_string, 변경 감지 | blind overwrite 방지, 낙관적 동시성 | 문자열이 일치해도 의미가 틀릴 수 있음 |
| Write | 기존 파일 선행 Read | 전체 덮어쓰기 사고 예방 | 새 파일 생성 범위/권한 오용 |
| Grep | 파일 목록 → 내용, 결과 상한 | 검색 비용과 컨텍스트 절약 | 놓친 파일, 인코딩, ignore 규칙 |
| Glob | 패턴 기반 파일 탐색 | 파일명을 좁혀 확인 | 규모가 크면 결과 정렬 편향 |
| Bash | 시간/출력 제한, 비대화형 실행 | 무한 대기·로그 폭증 방지 | 명령 주입, 환경변수 유출, 자식 프로세스 잔존 |

**Read→Edit 불변식**은 `revision_at_read == revision_at_commit`이라는 낙관적 동시성 제어와 유사하다. 예: 사용자가 파일을 읽은 직후 누군가 바꾸었으면 낡은 내용으로 덮지 않는다. 하지만 해시·mtime 확인 방식은 파일시스템과 경쟁 상태의 영향을 받을 수 있으므로 원자적 compare-and-swap 전략이 더 강하다. 또한 Linter가 성공했다고 논리적으로 올바른 구현인 것은 아니다. Syntax → Type → Unit → Integration → Behavioral acceptance 순서가 필요하다.

## 13. 계획이 발전하는 세 가지 방식 (p.32–33)

1. **Implicit planning**: 계획이 추론이나 대화 텍스트 안에만 존재한다. 출력이 쌓이면 목표가 사라질 수 있다.
2. **Plan-and-Execute**: 오케스트레이터가 별도 계획 객체를 쥐고 각 단계에 전용 에이전트를 호출한다. 단계별 책임이 분명하지만 계획의 경직성, 컨텍스트 재생성 부담이 있다.
3. **In-loop plan state**: 하나의 에이전트 루프에서 Todo/Task 도구가 상태를 업데이트한다. 피드백에 따라 재계획이 빠르다.

3이 항상 2보다 우수한 것은 아니다. 결제 승인, 규제된 업무 처리, 다수 서비스 간 사가(Saga)처럼 **비즈니스 상태 전이가 고정되어야 하는 문제**에서는 외부 오케스트레이션이 필수일 수 있다. 반면 코드 탐색·리팩토링처럼 가설과 탐색 경로가 변하는 작업은 내부 계획이 유연하다. **선택 기준은 '누가 다음 상태로 전이할 권한을 가지는가'다.** `in_progress` 개수 제한은 특정 Todo 도구의 정책이지 모든 작업 관리에 필수인 보편 법칙은 아니다.

## 14. Progressive Disclosure와 스킬 (p.34–35)

수백 개 도구의 장황한 스키마와 스킬 전문을 매번 보내면 토큰 비용뿐 아니라 도구 선택 오류가 늘어난다. 따라서 `Catalog → Detail → Reference / Script`를 단계적으로 연다.

```text
1. 작은 목차: deploy-api — API 배포 시 사용
2. 선택 후 SKILL.md: 배포 절차·주의 사항
3. 정말 필요할 때 references/prod-rollout.md
4. 검증된 scripts/check_rollout.py 실행
```

기술적으로는 **정보 검색 문제**와 **실행 권한 문제**가 결합된다. 스킬을 읽었다는 사실만으로 스킬 안의 임의 스크립트를 실행할 권한이 생겨선 안 된다. 스킬/플러그인은 공급망 위험을 가진 콘텐츠이므로 출처, 버전, 무결성, 도구 사용 권한을 따로 기록한다. 스킬 선택 성공률(retrieval precision)과 실행 성공률(task success)도 별개로 측정한다.

## 15. 프롬프트 캐싱의 원리는 '계층 이름'보다 '정확한 prefix'다 (p.36–40)

강의자료의 L1–L5는 원문의 **설명용 분류체계**다. L1=정체성/기본 수칙, L2=도구 계약, L3=세션 안내, L4=기억/환경, L5=변동 정보와 부가 규칙. 중요한 원칙은 변하지 않는 정보를 앞에 두고, 변하는 정보는 가능한 한 뒤로 보내는 것이다.

```
[정적 도구·정책·공용 프롬프트]
[세션 시작 시 고정한 프로젝트 정보]
[점점 누적되는 대화·도구 결과]
[새로운 이벤트/알림]
```

캐시 시스템은 보통 앞부분이 동일할 때 재사용 여지가 크다. 그러나 **[검증 필요]** 제공자별로 `tools → system → messages` 혹은 `system → tools → messages`라는 보편적인 단일 물리 직렬화 순서를 상정하기는 어렵다. API 메시지 필드와 서버 내부 토큰 직렬화·캐시 범위는 다를 수 있다. 특정 Claude Code 구현에서 관찰된 배열 배치를 모든 OpenAI·Qwen·Llama 런타임의 불변 법칙으로 일반화하면 안 된다.

### 캐시를 지키면서 환경 최신성을 지키는 법

- 시작 시 고정: CWD/OS/프로젝트 지침/사용자 선호처럼 요청의 기본 배경.
- 매 턴 동적: 현재 날짜, Git 변경, 새 MCP 서버 연결, 작업 진행률 등.
- **트레이드오프**: 스냅샷을 오래 고정하면 cache hit는 좋아지지만 정보가 오래될 수 있다. 정확성이 중요한 실행 전에는 도구로 최신 상태를 재조회한다.
- MCP 도구 자체의 스키마가 바뀌면 단순 메시지 첨부로 모델의 사용 가능한 실제 도구 목록을 업데이트한 것과 같지 않다. 도구 발견 지연(deferred tool discovery)과 도구 활성화 단계가 필요하다.

## 16. 컨텍스트 압축의 5단계 + 413 복구 (p.41–46)

**중요:** 강의자료는 여러 압축 방식을 묶어 보여주지만 일부는 공개 빌드에서 확인되는 동작, 일부는 내부 전용 흔적을 기반으로 재구성한 동작이라고 스스로 명시한다. 아래는 **설계 패턴으로 설명**한다.

### 16-1. Tool Result Budget: 원본을 디스크로 넘기고 미리보기만 모델에 제공

긴 Bash 로그를 prompt에 직접 넣는 대신 `preview + artifact reference`를 넣는다. 이는 VM의 page-out과 비슷하지만 정확히 동일하지는 않다. *원본 보존*이 가장 큰 장점이고, 경로와 특정 로그 구간을 다시 읽을 수 있어야 한다. **[원문 수치]** 50,000자 초과·한 턴 합계 200,000자·미리보기 2KB 등은 자료에 나온 구현값으로서 환경별 설정이 달라질 수 있다. 큰 응답을 저장할 때는 비밀정보 마스킹·아티팩트 TTL·접근 권한도 필요하다.

### 16-2. Snip: 모델이 불필요하다고 지정한 과거 메시지를 뷰에서 제거

핵심 아이디어는 **원본 이력과 LLM에 보여주는 투영(view)을 구분하는 것**이다. 모델이 오래된 실패 로그를 불필요하다고 판단하면 다음 API 요청에서 제외하지만 감사 기록은 유지한다. 모델이 필요한 사실까지 제거할 수 있으므로 중요한 정책·결정·미완료 작업은 보호하는 방식이 필요하다. **[검증 필요]** 강의자료도 이 방식의 내부 구현 상당 부분은 직접 확인 불가능하다고 밝힌다.

### 16-3. Microcompact: 오래된 도구 결과의 본문만 정리

최근 관찰값을 보존하고 오래된 상세 로그를 짧은 자리표시자로 바꾼다. **시간 기준**은 단순 오래됨이 아니라 프롬프트 캐시의 만료와 연결될 수 있다. `60분`·`최근 5개 보존`은 자료의 설명값이다. 로그를 없애기 전에 검색 가능한 원본 저장소가 있으면 복원성이 좋다. 최근 5개가 아니라 현재 작업에 필요한 5개를 보존하는 **중요도 기반 압축**도 고려할 수 있다.

### 16-4. Context Collapse: 오래된 구간을 비동기로 요약하고 전송 뷰만 교체

요약을 미리 만들어 `staged` 상태로 두고 임계치에서 확정(commit)하는 방식이다. 원본 대화와 요약된 뷰를 따로 유지하는 **event sourcing + materialized view** 같은 구조로 생각하면 이해하기 쉽다. 원본이 불변이면 감사·재생이 가능하지만 요약이 거짓이면 그 위에서 판단하는 모델이 오염될 수 있다. 요약마다 `source_span`, `summary_version`, `facts_preserved`, `checksum` 등을 기록하면 검증에 도움이 된다. **[검증 필요]** 이 방식의 내부 구현·트리거 수치는 자료에 따르면 공개적으로 완전 검증되지 않았다.

### 16-5. Auto-Compact: 전체를 축약하고 중요한 파일·계획을 다시 첨부

강의자료는 9섹션 요약과 'Compaction Amnesia'를 방지하는 최근 파일·계획·스킬 재주입을 설명한다. 추상적인 '요약해 줘' 대신 **목표, 제약, 이미 한 일, 증거, 실패, 파일, 미완료 항목, 현재 상태, 다음 행동**이 빠지지 않는 구조화 요약을 사용해야 한다.  
**문제:** 요약 후 맥락이 일부 유실되면 모델이 완료한 작업을 다시 하거나, 이전 사용자 요구를 잊을 수 있다.  
**대응:** 요약 전후에 acceptance criteria, pending tool call, permission, active file revision을 비교하는 불변식 검사를 수행한다.

### 16-6. Reactive Compact: 413 뒤 한정된 재시도

413(요청이 너무 큼)이 나면 압축을 시도하고 재호출할 수 있다. 단 같은 입력을 계속 요약·재시도하면 무한 비용이 된다. 반드시 1회 또는 정해진 상한으로 제한하고, 실패하면 사용자에게 명확한 오류를 반환해야 한다.  
**우선순위:** `원본 보존 → 손실 없는 결과 외부화 → 작은 관찰 정리 → 부분 요약 → 전체 요약 → 실패 처리`. 이 순서를 이해하는 것이 자료의 개별 임계치 숫자를 외우는 것보다 중요하다.

## 17. Recovery FSM과 Withholding (p.47–49)

상태 머신은 `RUNNING`, `WAITING_FOR_TOOL`, `RECOVERING`, `WAITING_FOR_APPROVAL`, `COMPLETED`, `FAILED`, `CANCELLED`처럼 현재 실행 상태와 허용 전이를 정의한다. 강의자료는 `next_turn`, `max_output_tokens_recovery`, `collapse_drain_retry`, `stop_hook_blocking`, `reactive_compact_retry`, `token_budget_continuation`, `max_output_tokens_escalate`, `model_fallback_retry`와 여러 terminal 사유를 열거한다. 이는 '하나의 예외 catch'가 아니라 **실패 종류별 다른 회복 정책**이 존재한다는 뜻이다.

| 사건 | 응답 행동 | 재시도 주의 |
|---|---|---|
| `tool_use` 성공 | 결과 추가 후 모델 재호출 | tool_use/tool_result ID를 맞춘다 |
| 출력 토큰 한도 | 충분한 슬롯으로 한 번 재호출 또는 이어쓰기 | 이미 적용한 side effect를 중복 실행하지 않는다 |
| 413 컨텍스트 초과 | 압축 후 재호출 | 무한 요약 차단 |
| 429/529 일시 장애 | jitter backoff/허용된 모델 fallback | rate limit 공정성, 예산 상한 |
| Stop hook 검증 실패 | 실패 증거를 첨부하여 수정 유도 | hook 실패가 영원한 루프를 만들지 않게 횟수 제한 |
| 사용자 취소 | 스트림/도구 중지 및 프로토콜 짝 보존 | 외부 side effect는 취소되었는지 확인 |
| 승인 거부 | 수행하지 않고 안전 종료/대안 제시 | 거절 후 다른 경로로 우회하면 안 됨 |

**Withholding**은 일시 오류를 복구하는 동안 사용자에게 불필요한 실패를 즉시 표시하지 않는 UX 접근이다. 단 **보안 거부·데이터 손실·지속 장애를 숨기는 것**은 다른 문제다. 실패 기록은 반드시 로그·트레이스로 보존하고, 복구가 확정되지 않은 작업을 성공이라고 표시하지 않는다. 스트리밍 중 일부 응답을 이미 사용자에게 전송했다면 재시도 후 중복 텍스트가 발생하지 않도록 출력 커밋 경계를 정의해야 한다.

### tool_use ↔ tool_result 무결성

모델 API는 도구 사용 요청과 해당 결과를 연결하는 규칙을 갖는다. 메시지 목록을 단순히 `[-100:]`으로 자르면 경계가 도구 결과 가운데 걸릴 수 있다. 따라서 **'논리적 대화 단위'를 유지**해야 한다. 미해결 호출은 취소/오류 결과를 붙여 프로토콜을 완성하거나, API별 허용되는 종료 방식을 준수한다. 단 가짜 tool_result를 생성할 때는 실제 실행 결과와 구분되는 명시적 상태가 필요하다.

## 18. 권한: 정적 규칙 + 빠른 분류 + 정밀 심사 + 인간 승인 (p.50–52)

첫 관문은 정책 엔진이다. 예를 들어 `deny`에 걸리면 모델이 아무리 '안전하다'고 해도 실행하지 않는다. 그 다음 명백하게 안전한 작업은 빠르게 통과시키고, 애매한 작업만 추가 심사를 거친다. 마지막에 사용자 승인을 요구한다.

**명령 예시:**

- `git status`: 읽기, 보통 저위험.
- `npm test`: 코드 실행으로서 임의 스크립트 실행 가능성이 있으므로 실제 권한은 저장소 신뢰도에 따라 달라짐.
- `git push -f`: 원격 히스토리 변경 가능, 높은 위험.
- `curl ...`: 외부 전송, 민감 데이터 유출 위험.
- `rm -rf`: 경로·권한·대상에 따라 파괴적.

**[중요]** 모델 분류기는 확률적이므로 '결정론적 권한 검증'의 대체물이 될 수 없다. 분류기의 `allow`는 실제 RBAC/ABAC, 대상 허용목록, 필수 승인, 네트워크 정책을 통과해야 한다. 또한 명령의 텍스트만 검사하면 명령 내부의 스크립트·심볼릭 링크·환경변수 확장·`sh -c` 우회가 가능하므로 실제 실행 환경이 최종 보안 경계다.

**[검증 필요]** 강의자료의 `93% 승인 피로`, `64토큰 0.2초`, `최대 4096 토큰`, `자동 모드 3-Tier` 등은 특정 버전/실험 결과를 확인해야 하는 숫자다. 지금 당장 가져와야 할 원칙은 **승인 피로를 줄이면서도 위험 작업에는 최소 권한과 강한 승인 절차를 강제**한다는 것이다.

# Part III. Module 03 — Nous Hermes Agent: 네 가지 기억과 학습 루프

## 19. '기억'은 하나의 저장소가 아니라 정보의 의미와 수명에 따른 네 유형이다 (p.53–57)

| 유형 | 대표 저장 방식 | 질문 | 실무 불변식 |
|---|---|---|---|
| L1 Working | 현재 메시지·Todo | 지금 무엇을 하고 있는가? | 현재 실행에 필요한 상태가 유실되지 않음 |
| L2 Episodic | 영속 transcript + 검색 색인 | 과거에 언제 무엇을 했는가? | 원본 근거를 다시 찾을 수 있음 |
| L3 Semantic | 요약 사실·선호도 메모 | 어떤 사실을 늘 기억해야 하는가? | 오래된 정보/모순을 통제 |
| L4 Procedural | 재사용 가능한 SKILL.md | 반복 문제를 어떻게 푸는가? | 절차가 검증 가능하고 소유권이 분명함 |

L2와 L3의 차이는 중요하다. “지난주 금요일 배포 때 Pod가 OOMKill 되었다”는 **사건**이고, “이 서비스는 메모리 상한이 작아서 배치 처리 시 분할이 필요하다”는 **일반화된 지식**이다. L4는 그 지식을 바탕으로 “OOMKill 조사 절차”라는 재사용 매뉴얼이 된다. *사건 → 사실 → 절차* 승격을 모델에 무조건 맡기면 일회성 노이즈가 잘못된 영구 규칙이 된다. 반복성·근거·사용자 승인·성공 검증을 고려해야 한다.

## 20. L2 Episodic: append-only transcript와 검색 색인을 구분한다 (p.58–60)

대화 원문은 즉시 영속 기록으로 저장하고, 나중에 별도 요약/검색 인덱스를 만든다. 쓰기 경로에서 원문 보존을 우선하면 요약 작업 실패 시에도 진실의 원천(source of truth)이 남는다. FTS5는 문자열·토큰 기반 검색에 강하지만 표현이 다른 동의어·축약어·철자 변형은 별도 전처리나 임베딩/하이브리드 검색이 필요할 수 있다. 한국어 토큰화와 코드 심볼 검색도 따로 설계해야 한다.

### Push 힌트 → Pull 원문

먼저 관련 세션의 2~3줄 힌트만 보여주고, 모델이 정확한 옵션이나 오류 문구를 요구하면 `session_recall`로 원문을 가져온다. 자료의 **앞 3개 + anchor ±5개 + 뒤 3개** 전략은 훌륭한 예시다. 앞부분은 최초 목표, 가운데는 증거와 문제 해결, 끝부분은 결론을 복원한다. 하지만 anchor를 잘못 찾으면 틀린 결론을 자신 있게 재생할 수 있다. 결과에 세션 ID, 타임스탬프, 메시지 ID, 출처를 함께 제공해야 한다.

## 21. L3 Semantic: 작은 사실 메모와 동결 스냅샷 (p.61–62)

강의자료는 `MEMORY.md` 2,200자, `USER.md` 1,375자의 상한을 제시한다. 대화 중 수정은 파일에 반영하지만 시스템 프롬프트는 세션 시작 시 스냅샷으로 고정한다. 캐시 보존과 최신성 사이의 절충이다. 이번 세션에서 방금 알려진 사실은 messages에 남으므로 모델이 사용할 수 있지만, **도구가 직접 최신 메모를 조회하는 경우**에는 파일과 프롬프트 사이 내용이 달라질 수 있다. 이때 어떤 저장소가 우선인지 규칙이 필요하다.

### 메모리 오염 방지

- `source`: 누가 말했는가? 사용자·도구·외부 웹·추론 중 어느 것인가?
- `confidence`: 직접 확인한 사실인가, 모델 추정인가?
- `updated_at`과 `expires_at`: 오래된 정책/상태는 폐기 또는 재검증.
- `consent`와 `ownership`: 사용자 소유 메모리는 백그라운드 작업이 임의 삭제·수정하지 못하게 함.
- `version`: 어떤 버전의 메모리가 어떤 판단에 사용되었는가?

백그라운드 리뷰가 `add`는 즉시 실행하고 `replace/remove`는 승인 대기열에 넣는 구조는 파괴적 메모리 변경을 늦추는 전략이다. 하지만 무제한 add도 중복·개인정보 오염을 일으킬 수 있으므로 품질 게이트는 필요하다.

## 22. L4 Procedural: 스킬은 기억된 사실이 아니라 '반복 가능한 절차'다 (p.63–64)

`skills/deploy-api/SKILL.md`, `references/`, `scripts/`, `.usage.json`처럼 구성된다. 목차는 세션 시작 시 보이고, 본문은 `skill_view`로 열어본다. 에이전트가 10개 도구를 호출한 복잡한 작업을 마친 뒤 재사용 가능한 스킬로 요약할 수 있다. 하지만 '도구 10회'는 학습 필요성의 대리 지표일 뿐이다. **많이 호출했다고 성공적이고 일반화 가능한 해결 절차인 것은 아니다.** 바람직한 조건은 명확한 입력 조건, 성공 기준, 실패 사례, 반복 가능성, 검증된 스크립트, 적절한 접근 권한이다.

### 스킬에 반드시 있어야 할 설계 정보

```markdown
---
name: incident-triage
summary: API 5xx 급증 상황에서 원인 범위를 좁힌다
---
## Preconditions
- 대상 서비스에 대한 읽기 권한
- 배포 시간과 요청량 지표 접근 가능
## Steps
1. 5xx 증가 시점 및 영향 범위 확인
2. 배포/설정 변경과 시간 상관관계 비교
3. 에러 traceId별로 같은 root cause를 묶음
4. 재현 가능하면 작은 환경에서 검증
## Never
- 사용자 승인 없는 운영 DB 변경
- 프로덕션 로그의 개인정보 외부 전송
## Success checks
- 에러율 감소뿐 아니라 원인이 실증적으로 확인됨
## Evidence
- 대시보드 URL/로그 검색 쿼리/트레이스 ID
```

## 23. Closed Learning Loop와 사용자 피드백 (p.54, p.64)

사용자의 “그 방식 틀렸어” 같은 교정은 유익하지만 반드시 일반화해야 하는 법칙은 아니다. 예를 들어 ‘이번 면접 답변은 짧게’는 **이번 작업 제한**일 수 있고 ‘앞으로 모든 답변은 짧게’는 **지속 선호**일 수 있다. 둘을 구분하지 않으면 잘못된 기억이 축적된다. 새로운 스킬을 만들기보다 먼저 기존 스킬을 patch하고, 세부 예외는 references로 내린다는 우선순위는 스킬 폭증을 완화한다.

백그라운드 리뷰는 사용자 요청 처리보다 낮은 우선순위로 배치하고, 기록이 완전히 저장된 뒤에 시작한다. 이때 동시에 두 리뷰가 같은 파일을 수정할 수 있으므로 `expected_version`이 있는 CAS, 파일 잠금 또는 단일 writer 큐를 사용한다.

## 24. Curator: 기억을 만드는 기능만큼 '버리는 기능'이 중요하다 (p.65–67)

Curator는 비슷한 스킬을 대표 상위 스킬로 합치고 오래 안 쓴 스킬을 보관한다. 자료에는 `7일 주기 + 2시간 유휴`, `14일 stale`, `30일 archive`라는 정책이 나온다. **이 값은 예시로 이해**해야 한다. 월별 결산처럼 한 달에 한 번만 필요한 핵심 스킬은 30일간 사용되지 않았다고 가치가 없는 것이 아니다. 따라서 사용 빈도 외에도 최근 성공률, 업무 중요도, 사용자 고정(pin), 장애 시 복구 가치, 대체 스킬 존재 여부를 보아야 한다.

### Umbrella consolidation

`git-commit`, `git-push`, `git-pr-labels`라는 좁은 스킬을 `git-workflow`라는 공통 진입점으로 합친다. 본문은 공통 절차, references는 세부 규칙으로 분리한다. 원본은 삭제하지 않고 archive하고, `absorbed_into` 연결을 남긴다. 중요한 점은 **모든 스킬을 하나로 모으는 게 아니라 선택의 단위를 적절히 만들기**다. 관련이 적은 배포·롤백·보안 감사까지 하나에 넣으면 반대로 retrieval precision이 떨어진다.

### 기억 시스템에서 추가로 설계할 것

삭제 요청이 들어왔을 때 transcript, 검색 색인, 요약, 캐시, 스킬 학습 결과, 백업을 어디까지 삭제해야 하는가? 다중 사용자나 조직에서 메모리의 tenant isolation은 어떻게 보장하는가? 개인 정보가 스킬에 무심코 포함되지 않았는가? 장기 기억 시스템은 검색 품질뿐 아니라 정보 생명주기와 접근 통제까지 포함한다.

# Part IV. Module 04 — OpenManus와 OpenClaw

## 25. OpenManus의 4단 상속 구조 (p.68–70)

`BaseAgent → ReActAgent → ToolCallAgent → Manus/전문 에이전트`는 역할별 추상화를 보여준다. BaseAgent는 상태와 run 루프, ReActAgent는 think/act, ToolCallAgent는 구조화된 도구 호출과 결과 누적, Manus는 도구 묶음과 목적별 프롬프트를 제공한다. 관심사 분리가 직관적이라는 장점이 있지만, 상속이 깊어지면 부모 클래스의 상태/예외 처리 규칙이 자식에 숨어 테스트가 어려워질 수 있다. 조합(composition)과 전략 객체로 대체할 지점도 검토해야 한다.

### CodeAct: 도구 호출 횟수 대신 하나의 코드 실행

10개 행을 순회하는 데 매 행마다 LLM을 호출하는 것보다, LLM이 한 번 생성한 스크립트가 전체 계산을 수행하는 편이 빠를 수 있다. 그러나 스크립트 실행으로 바꾸면 **모델 호출 비용은 감소하는 대신 코드 실행 권한이라는 큰 공격 표면**이 생긴다. 사전에 만들어 둔 검증된 스크립트/함수는 임의 생성 코드를 실행하는 것보다 일반적으로 안전하다. 사용자별 네트워크·파일 접근 제한과 CPU/메모리/time quota가 중요하다.

## 26. PlanningFlow와 TAG 라우팅 (p.71)

`[SEARCH] → [DATA_ANALYSIS] → [REPORT]`처럼 계획에 타입을 지정하고 정규식으로 담당 에이전트를 선택한다. 장점은 **라우팅 비용이 거의 0**이고 단계의 진행률을 외부에서 관리한다는 것이다. 하지만 문자열 태그를 모델이 잘못 출력하거나 예상 밖의 유형을 만들면 잘못 라우팅된다. 실제 서비스라면 문자열 파싱보다 `enum task_type`, JSON 스키마, 등록된 라우팅 테이블로 강하게 검증하는 편이 좋다. 

**설계 질문:** 어떤 계획 단계가 끝났는지 모델이 선언하는가, 산출물 검증기가 선언하는가? 실패한 단계를 몇 번 반복하는가? 단계끼리 의존성을 갖는 DAG인가, 한 줄짜리 순차 리스트인가? 작업 중 요구사항이 바뀌면 이미 끝난 단계를 무효화하는가?

## 27. 실행 환경: 프로세스·Docker·클라우드 VM (p.72)

강의자료는 로컬 Python 실행, Docker, Daytona 기반 가상 PC로 격리/작업 능력을 늘린다고 설명한다. **[해설]** 이것은 위험도별 선택지이며 'Docker=완전한 보안'은 아니다. 컨테이너 탈출 가능성, 공유 커널, 호스트 마운트, 소켓 바인딩, privileged 모드, 네트워크 접근, 자격 증명 전달을 확인해야 한다. GUI 작업은 스크린샷에 비밀 정보가 담길 수 있고, 좌표 기반 클릭은 화면 변경/팝업에 취약하다. 클릭 직전에 대상·화면을 재검증하고 비가역적 동작에는 사용자 승인을 두는 것이 좋다.

MCP Client는 외부 도구를 소비하고 MCP Server는 자신이 제공하는 도구를 노출한다. **도구를 연결할 수 있다는 것과 도구를 신뢰할 수 있다는 것은 다른 문제**다. 이름 충돌, tool description의 프롬프트 인젝션, API 키 범위, rate limit, 서버 identity를 검사해야 한다.

## 28. 프로토타입 코드에서 드러나는 네 결함 (p.73)

1. `messages[-100:]` 슬라이싱: tool call과 result를 분리해 프로토콜 오류. **해법**: 완전한 논리 메시지 그룹 단위로 보존, 경계 검증.
2. `content`만 비교하는 루프 감지: 내용이 빈 메시지의 같은 도구 호출을 놓침. **해법**: `tool_name + canonicalized_arguments + observed_result + state_delta`를 비교.
3. `finally`에서 상태를 이전 값으로 돌림: 정상 `FINISHED` 신호를 부모가 보지 못함. **해법**: 상태 전이표를 명확히 하고 완료를 영속 기록.
4. 검색 폴백·로컬 Python 실행: 오류를 제대로 분류하지 못하면 fallback으로 전이 못함; Python `exec`는 위험. **해법**: 오류 유형별 폴백 정책, 샌드박스 의무화.

이 중 핵심은 **데모 성공과 프로덕션의 시간적·동시성·보안적 정확성은 다르다**는 것이다. 5번의 정상 호출에서는 드러나지 않는 오류가 5,000번의 재시도와 장애 복구 과정에서 드러난다.

## 29. OpenClaw의 Gateway와 SessionKey (p.74)

입력 채널(메신저/웹/폰)을 표준화한 SessionKey로 정규화한다. 이 식별자는 **메시지가 어느 세션에 합류하는지와 응답을 어디로 보낼지** 정하는 데 중요하다. 하지만 강의자료의 표현처럼 '세션 키 자체가 권한을 결정한다'고 단순화해서는 안 된다. 실제 권한은 인증된 발신자, tenant, 방 유형, 정책, 토큰 스코프의 검증 결과에서 도출해야 한다. 유저가 SessionKey를 임의로 조합해 다른 사람의 기억을 읽을 수 있다면 심각한 취약점이다. SessionKey는 신원 그 자체가 아니라 **검증된 주체를 기준으로 서버가 구성하는 라우팅 키**로 다루어야 한다.

## 30. Session lane: 왜 같은 방은 직렬화하고 다른 방은 병렬화하는가? (p.75)

같은 세션에서 동시에 두 입력을 처리하면 각각 다른 최신 상태를 읽고 같은 메모리를 덮어쓸 수 있다. 따라서 SessionKey별 `maxConcurrent=1`이라는 직렬화 정책은 순서·일관성을 확보하는 간단한 전략이다. 다른 세션은 병렬로 실행해 전체 처리량을 얻는다. 그러나 같은 세션을 다른 워커 프로세스에 동시에 배정하면 **프로세스 내부 mutex만으로 충분하지 않다**. 분산 락, durable queue, DB advisory lock, actor-per-key routing 등 하나를 선택해야 한다.

**백그라운드 서브에이전트 결과**는 작업 중인 모델의 입력을 갑자기 바꾸지 않고 다음 턴에 이벤트로 합류시키는 방식이 일관성을 유지한다. 이때 중복 알림 방지를 위해 event_id와 idempotent apply가 필요하다. cron 작업이 같은 레인에서 자신의 완료를 기다리는 데드락을 막기 위해 별도 레인 또는 논블로킹 전이가 필요하다.

## 31. Heartbeat: 선제적 감시와 스팸 없는 알림 (p.76)

자료는 30분마다 점검하고 `HEARTBEAT_OK`라는 무음 토큰을 사용한다고 설명한다. **[최신 문서와의 차이]** 2026-11 공식 OpenClaw 문서는 기본 Heartbeat의 조용한 응답으로 `NO_REPLY`를 사용하고 기존 `HEARTBEAT_OK`도 호환한다고 설명한다. 최신 구현에서 Heartbeat는 자동화 스케줄러가 소유하는 system-owned job이며, '항상 별도의 30분 타이머 프로세스'로 단순화하면 부정확하다. 기본 30분은 설정·인증 방식에 따라 달라질 수 있다.

비용을 계산할 때 `실행 횟수 × 1회 입력 토큰 × 단가`뿐 아니라, 외부 API 호출 비용과 이벤트 없는 폴링의 비율을 포함한다. 가능하면 webhook/event-driven notification으로 전환하고, 주기적 점검에는 active hours, cooldown, deduplication, severity threshold, silence token을 둔다. **최신 공식 문서**: https://github.com/openclaw/openclaw/blob/main/docs/gateway/heartbeat.md

## 32. 외부 입력, 프롬프트 인젝션, 기억 오염 (p.77)

외부 메신저·웹페이지·문서에서 들어온 내용은 **데이터이지 명령이 아니다**. 방에 있는 사람의 신원을 검증하지 않은 채 도구 실행으로 연결하면 권한 상승이 발생한다. 강의자료는 `페어링 → 세션 범위 → 원격 승인`과 `taint` 마킹을 설명한다. 설계의 큰 틀은 **출처(provenance)를 따라 권한이 전염되거나 확대되지 않도록 한다**는 것이다.

```
웹페이지/외부문서 (untrusted)
  ↓
읽기 전용 결과 (source=web, trust=untrusted)
  ↓
LLM 요약·추론 (derived_from=untrusted)
  ↓
장기 메모리 기록 시 검토 → 승인 전에는 자동 상시 주입 금지
```

`taint` 한 비트로 모든 위험이 해결되는 것은 아니다. 여러 출처가 섞인 경우, 사용자가 직접 승인한 부분, 외부 파일의 코드 블록, RAG 검색 결과까지 추적해야 할 수 있다. 특히 모델이 만든 '요약'에는 원문보다 더 그럴듯한 거짓 지시가 포함될 수 있으므로, 요약 결과도 원래 입력의 trust label을 상속시키는 보수적 정책이 필요하다.

## 33. OpenManus vs OpenClaw를 적절히 비교하는 법 (p.78)

**[원문 요지]** OpenManus는 빠르게 작업 공간/계획형 에이전트를 구성하는 대표 사례, OpenClaw는 상시 가동·멀티채널·동시성·보안을 강조하는 사례다. 하지만 'A는 데모용, B는 완벽한 프로덕션'이라는 이분법은 피해야 한다. 실제 배포 품질은 사용 버전, 운영 설정, sandbox, secret management, 모니터링, 테스트, 패치 수준에 달려 있다. 비교할 것은 브랜드 서열이 아니라 **필요한 런타임 불변식을 얼마나 충족하는가**다.

## 34. 프로덕션 에이전트의 권장 책임 경계

```text
Ingress / API Gateway
  - 인증, 요청 스키마, rate limit, request_id, tenant
    ↓
Session & Conversation Store
  - thread_id, snapshot/version, user consent, pending job
    ↓
Agent Coordinator
  - goal, task state, dependency DAG, deadline/budget
    ↓
LLM Adapter
  - provider, model fallback, prompt/cache, streaming
    ↓
Tool Policy Gate (신뢰 경계)
  - RBAC/ABAC, argument validation, allowlist, HITL
    ↓
Execution / Sandbox
  - filesystem, HTTP, DB, MCP, remote computer
    ↓
Result Verifier
  - schema, expected effect, tests, anomaly detection
    ↓
Event Log + Memory Pipeline
  - tool call/result durable pairs, summaries, long-term skills
    ↓
Response / Streaming Gateway
  - output commit, SSE reconnection, deduplication
```

**규칙:** LLM은 tool call을 **제안**하고, 정책 엔진은 실제 실행 여부를 **판단**하며, 실행기는 부작용을 **수행**하고, 검증기는 목표 충족 여부를 **평가**한다. 이 네 가지를 같은 함수의 프롬프트로 혼합하지 않는다.

## 35. Tool Invocation을 실제 상태 머신으로 모델링

| 상태 | 허용 전이 | 내구성·중복 처리 |
|---|---|---|
| PROPOSED | VALIDATED / REJECTED | tool_call_id, normalized args 기록 |
| VALIDATED | APPROVAL_REQUIRED / APPROVED / REJECTED | principal·resource·policy_version 기록 |
| APPROVAL_REQUIRED | APPROVED / REJECTED / EXPIRED | 승인자·서명된 인자 해시 기록 |
| APPROVED | RUNNING | 재시작 시 중복 실행 방지 키 확보 |
| RUNNING | SUCCEEDED / FAILED / UNKNOWN | 외부 시스템의 실제 커밋 여부 조회 |
| FAILED | RETRY_WAIT / COMPENSATING / TERMINAL | 재시도 허용 여부와 오류 분류 |
| SUCCEEDED | VERIFIED / VERIFY_FAILED | 산출물 검증, external effect id |
| VERIFIED | RECORDED | result를 LLM 메시지와 감사 로그에 반영 |

특히 분산 시스템에서 `timeout`은 **실행되지 않았다는 뜻이 아니다**. 요청이 외부 서비스에 도달해 성공했지만 응답만 유실될 수 있다. 이 상태는 `UNKNOWN`이다. 결제·메일·프로비저닝에는 idempotency key, 조회 API, outbox, saga, reconciliation 같은 설계가 필요하다.

## 36. 실제로 측정해야 할 SLI/SLO

| 범주 | 추천 지표 | 왜 필요한가 |
|---|---|---|
| 성공 | Acceptance pass rate, task completion | 모델이 완료 선언한 비율과 실제 성공을 구분 |
| 비용 | token / cost per successful task | 실패 루프를 포함한 단가 |
| 지연 | TTFT, time-to-task-complete, P95 tool latency | 첫 글자와 실제 완료 시간은 다름 |
| 루프 | repeated tool call ratio, no-progress steps | 목표 표류와 중복 재호출 탐지 |
| 복구 | auto-recovery success, retries per failure | 회복 품질과 오류 은닉 범위 |
| 안전 | denied unsafe tool call, approval override, policy bypass | 보안 실패 경향 |
| 컨텍스트 | cache hit rate, compaction rate, retrieval quality | 비용과 기억 손실 균형 |
| 메모리 | memory precision, stale-memory use, provenance coverage | 잘못된 장기 기억의 피해 예방 |
| 운영 | queue lag, active workers, stuck sessions, dead letters | 상시 에이전트의 큐·동시성 품질 |

SLO를 정할 때 `답변을 생성했다`와 `사용자의 목표를 완료했다`는 별개의 이벤트로 취급해야 한다. 예를 들어 'SSE 첫 토큰 전송 성공'은 메시지 생성 SLI이며 실제 외부 시스템의 상태 변경 성공률을 보장하지 않는다.

## 38. 직접 만들어볼 최소 하네스 실습 순서

### 단계 A — Naive ReAct 구현 및 실패 재현
- 세 가지 도구: `search_docs`, `read_file`, `write_temp_file`.
- 도구 오류 반복, 빈 도구 결과, 잘못된 인자, 40KB 로그, API timeout을 인위적으로 발생시킨다.
- step budget이 없을 때와 있을 때의 토큰/비용 차이를 관찰한다.

### 단계 B — Middleware·Runtime Context
- 인증된 principal을 out-of-band로 주입한다.
- `before_model`에서 현재 목표와 토큰 예산을 구성한다.
- `wrap_tool_call`에서 권한과 인자를 검증한다.
- `after_agent`에서 감사 로그를 저장한다.
- 동일 테스트를 LLM Mock으로 실행해 정책 모듈을 독립 검증한다.

### 단계 C — ACI·복구·압축
- `Read(offset,limit)`, `Edit(old_string,new_string,revision)`을 구현한다.
- 긴 결과를 디스크에 저장하고 프롬프트에는 미리보기만 남긴다.
- 컴팩션 전후에 테스트·계획·사용자 제약이 유지되는지 검사한다.
- 413과 429를 주입해 각기 다른 복구 FSM이 동작하는지 확인한다.

### 단계 D — Hermes식 Memory
- 원문 append-only transcript와 키워드 검색 색인을 분리한다.
- 매 세션 시작의 frozen semantic snapshot을 비교한다.
- 사용자 피드백을 스킬 개선 제안으로 만들되 승인 후 적용한다.
- 잘못된 기억과 중복 스킬을 복구 가능한 archive로 이동한다.

### 단계 E — OpenClaw식 장기 실행
- SessionKey별 순차 큐를 만들고 서로 다른 세션 간 병렬 실행을 허용한다.
- 중복 이벤트, 워커 재시작, 배포 중단, 늦게 도착하는 서브에이전트 결과를 시험한다.
- 허용된 외부 이벤트만 작업을 시작하게 하고 변경 작업은 승인 게이트를 거친다.
- 이상 없음을 알리는 heartbeat는 사용자 메시지로 전송하지 않는다.

## 39. 자료에 대한 주요 정정·검증 메모

1. 원문의 “O(N²) 지수 폭증”은 수학적으로 부정확하다. 반복당 일정한 이력이 추가되는 경우는 **이차 증가**다.
2. **98.4% 하네스 / 1.6% LLM**은 일반 법칙이 아니라 특정 코드·계산 기준에 대한 자료상의 주장이다.
3. Claude Code의 **캐시 100% 적중·비용 90% 절감**은 보편 보증이 아니라 조건부 최적화 목표다.
4. 강의자료도 **Snip, Collapse, Reactive Compact** 등의 일부 구현을 내부 전용 흔적으로 재구성했다고 밝힌다. 확인된 오픈소스 API처럼 설명하지 않는다.
5. `Git worktree`는 코드 변경을 분리해도 OS/권한 수준의 보안 샌드박스를 제공하지 않는다.
6. `ToolRuntime.context`의 LLM 스키마 비노출은 사용자 인증과 비밀정보 유출 방지를 자동 보장하지 않는다.
7. **특정 모델 제공자별 메시지 직렬화 순서**는 SDK·제공자·버전별 차이를 고려해야 한다.
8. OpenClaw Heartbeat의 **현재 기본 조용한 응답은 `NO_REPLY`**, `HEARTBEAT_OK`는 호환 경로로 공식 문서에 설명되어 있다(2026-11 확인).
9. 'OpenManus는 프로토타입, OpenClaw는 프로덕션'은 강의의 비교 프레임이지 보안 품질·운영 준비도에 대한 무조건적 인증이 아니다.
10. 자료 속 고정 숫자(임계치·토큰·파일 길이·모드·함수 이름)는 **실제 사용 버전을 고정한 뒤** 공식 코드와 비교해야 한다.
